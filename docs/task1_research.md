# Задание 1. Исследование моделей и инфраструктуры для RAG-бота QuantumForge Software

## 0. Контекст: кто ставит задачу и для кого решение

**Заказчик** - руководство QuantumForge (CTO / Head of Engineering) и GRC-команда: им нужны измеримые эффекты - меньше часов на поиск, быстрый онбординг, 140 часов подготовки к SOC 2 ревью, объективная картина пробелов в документации.

**Пользователи** - четыре роли с разными запросами: разработчики (архитектура, API, микросервисы), саппорт (типовые проблемы клиентов), менеджеры и аналитики (регламенты, бизнес-правила), новые сотрудники (onboarding).

**Ограничения, которые влияют на выбор стека:**

| Ограничение | Следствие |
|---|---|
| Компания финско-эстонская (ЕС) - GDPR, годовой SOC 2 | Данные сотрудников и клиентов нельзя отправлять провайдеру без DPA и EU data residency; российские облака (Yandex Cloud) для этой компании юридически непроходной вариант |
| В базе есть Terraform state, Helm charts, интеграции со SCADA клиентов (ABB, Wärtsilä), 250 PDF заказных спецификаций | Часть материалов конфиденциальна - для них нужен локальный контур, в облако уходить не должны |
| Объём: ~18 000 MD/MDX + ~3 000 Confluence + 250 PDF ≈ 21 000 документов (оценочно 15-20 млн токенов), прирост ~400 страниц/мес | Индексация должна быть дешёвой и инкрементальной; полная переиндексация - часы, а не дни |
| Уже есть AWS (EKS + RDS), ArgoCD, GitHub Actions | Разворачивать в существующем EKS, не заводить новую платформу |
| Дубли и расхождение версий между Confluence / Notion / PDF | Бот должен цитировать источник и дату, а не «усреднять» противоречия |

Оценка нагрузки для расчёта стоимости: ~200 сотрудников × 10 запросов/день = **2 000 запросов/день**; один запрос ≈ 3 000 токенов на вход (контекст из 4-6 чанков + few-shot) и ≈ 400 на выход.

## 1. Сравнение LLM: локальные Hugging Face vs облачные

| Критерий | Локальные (Llama 3.1 8B / 70B, Qwen2.5, Mistral) | OpenAI (GPT-4o mini / GPT-4.1) | Anthropic Claude (Haiku 5.5 / Sonnet 5.5) | YandexGPT (Lite / Pro 5.1) |
|---|---|---|---|---|
| Качество ответов на RAG | 8B - заметно слабее, путает факты в длинном контексте; 70B - сопоставимо с GPT-4o mini, но нужна дорогая GPU | Высокое, хорошо следует инструкциям и формату (CoT, цитирование) | Высокое, длинный контекст 200K, уверенно держит формат и отказы «не знаю» | Хорошее на русском, слабее на английской технической документации (а у QuantumForge база на английском) |
| Скорость | Зависит от GPU: 8B на L4 ~30-50 ток/с; 70B на 2×A100 ~15-20 ток/с; холодный старт модели минуты | 1-3 с на ответ, без своей инфраструктуры | 1-3 с (Haiku), 3-6 с (Sonnet) | 2-5 с |
| Стоимость при 2 000 запросов/день (6M вход + 0.8M выход в день) | Железо: 1×L4 (8B) ≈ $400-600/мес в облаке; 2×A100 (70B) ≈ $3 000-5 000/мес или $30-40k капитальных затрат + инженер на поддержку | gpt-4o mini: $0.15/$0.60 за 1M -> ≈ $1.4/день ≈ **$40/мес**; gpt-4.1-mini ≈ $110/мес | Haiku 5.5: от $0.10/$0.50 за 1M -> ≈ **$30/мес**; Sonnet 5.5: $2/$10 -> ≈ $600/мес | Lite ≈ $1.64 за 1M -> ≈ $340/мес; Pro 5.1 ≈ $6.6 за 1M -> ≈ $1 350/мес |
| Развёртывание | Нужен GPU-нод в EKS (nvidia device plugin), vLLM/TGI, мониторинг VRAM, обновление весов - 1-2 недели работы DevOps + ML-инженера | Ключ + SDK, EU data residency по запросу, DPA есть | Ключ + SDK, DPA и SOC 2 есть; батч-режим дешевле вдвое | Ключ в Yandex Cloud; данные обрабатываются в РФ - для компании из ЕС это блокер по GDPR |
| Конфиденциальность | Данные не покидают контур - единственный вариант для чувствительных документов | Данные уходят провайдеру (не используются для обучения по API, но это всё равно передача за пределы контура) | То же | То же + юрисдикция РФ |

**Вывод по LLM.** Для 80% базы (публичная документация, регламенты, onboarding) облачная модель младшего класса (Claude Haiku 5.5 или GPT-4o mini) даёт лучшее качество за $30-40/мес - в 10-100 раз дешевле собственного GPU-кластера. Для конфиденциального подмножества (Terraform state, клиентские интеграции, SOC 2 политики) нужна локальная модель 8B на одном L4/A10G - качества «найти и процитировать регламент» хватает, а данные не уходят. YandexGPT для этой компании отпадает по юрисдикции.

## 2. Сравнение моделей эмбеддингов

| Критерий | Локальные Sentence-Transformers (all-MiniLM-L6-v2, bge-base-en-v1.5, bge-m3) | OpenAI Embeddings (text-embedding-3-small / large) | Yandex Embeddings |
|---|---|---|---|
| Скорость создания индекса (20 млн токенов) | MiniLM на CPU (8 vCPU): ~1 500 чанков/мин -> ~1 час на всю базу; bge-base на GPU L4: ~10 минут; bge-m3 (568M) на CPU - часы, нужна GPU | Ограничено rate limit (~1M ток/мин на tier 2) -> ~20-30 минут, параллельными батчами | Аналогично, ~30-60 минут |
| Качество поиска (MTEB retrieval, англ.) | MiniLM ≈ 42 (384-d, слабее на длинных технических текстах); bge-base ≈ 53; bge-m3 ≈ 55, мультиязычная (пригодится для русскоязычного саппорта) | 3-small ≈ 51 (1536-d), 3-large ≈ 55 (3072-d) | Хорошо на русском, уступает на английской технической лексике |
| Стоимость владения | Бесплатно; CPU-нод уже есть; переиндексация 400 страниц/мес - минуты | 3-small $0.02/1M -> полная база ≈ **$0.40**, прирост - копейки; но каждый запрос пользователя тоже эмбеддится (2 000/день - ≈ $0.01/день) | ≈ $0.08/1M -> $1.6 за базу |
| Риски | Нужно самим следить за версией модели: смена модели = полная переиндексация | Зависимость от API: если провайдер снимет модель с поддержки - переиндексация; содержимое чанков уходит провайдеру (в т.ч. конфиденциальных) | Юрисдикция РФ |

**Вывод по эмбеддингам.** Стоимость облачных эмбеддингов ничтожна, но они отправляют *весь корпус* провайдеру - включая конфиденциальные документы, которые мы не хотим выносить. Локальная **bge-base-en-v1.5** (или bge-m3, если нужна русская лексика для саппорта) даёт качество уровня text-embedding-3-small, работает на CPU-нодах EKS и не создаёт зависимости от внешнего API. В учебном проекте использована all-MiniLM-L6-v2 - она в 3 раза быстрее на CPU и для базы из 55 документов разницы в качестве нет; в проде стоит заменить на bge-base (та же библиотека, одна строка).

## 3. Сравнение векторных хранилищ: FAISS vs ChromaDB

| Критерий | FAISS (библиотека) | ChromaDB (БД) |
|---|---|---|
| Что это | Библиотека Meta для ANN-поиска: индекс в памяти процесса, сохраняется в файл | Embedded/клиент-серверная векторная БД поверх SQLite (+HNSW из hnswlib), с коллекциями, метаданными и фильтрами |
| Скорость поиска | Лучшая в классе: IndexFlatIP точный поиск по 100k векторов ~1 мс; HNSW/IVF - микросекунды на миллионах; GPU-версия | HNSW - миллисекунды на сотнях тысяч; на миллионах заметно медленнее FAISS, SQLite становится узким местом |
| Скорость индексации | Мгновенная для Flat; обучение IVF - минуты | Вставка батчами, ~2-5k векторов/с; при больших объёмах нужно шардировать |
| Инкрементальные обновления | Добавить можно, удалить/обновить - нет (нужно пересобирать индекс или вести tombstone-список) | Есть `upsert`/`delete` по id - критично при приросте 400 страниц/мес и устаревающих страницах |
| Фильтрация по метаданным | Нет (делается руками поверх результатов) | Есть `where`-фильтры: по роли пользователя, пространству Confluence, дате, уровню конфиденциальности |
| Сложность внедрения и поддержки | Минимальная для одного процесса; но для нескольких реплик бота нужно самим решать, как шарить индекс (файл в S3 + перезагрузка) | Запускается как контейнер в EKS, persistent volume, HTTP API; один сервис на все реплики бота |
| Удобство | Низкоуровневый API, нужно самому хранить тексты и метаданные (у нас `chunks.pkl`) | Высокоуровневый API, LangChain-интеграция, документы+метаданные+векторы в одном месте |
| Стоимость владения | 0, память под индекс: 589 чанков × 384 float32 ≈ 0.9 МБ; для 150k чанков прод-базы ≈ 230 МБ | 0 лицензий, ~1 под в EKS (2 vCPU, 4 ГБ) + PV 10-20 ГБ |
| Когда выбирать | Прототип, одна реплика, редкие обновления, максимальная скорость | Прод с инкрементальными обновлениями, несколькими репликами, фильтрами по правам доступа |

**Вывод по хранилищу.** Для проектной работы - **FAISS**: нулевая эксплуатационная сложность, индекс строится за 20 секунд и живёт в Docker-томе. Для прода QuantumForge - **ChromaDB** (или Qdrant как следующая ступень): нужны фильтры по уровню конфиденциальности и роли, ежедневные upsert из Confluence/GitHub и несколько реплик бота. Код проекта написан так, чтобы хранилище менялось в одном модуле (`rag_bot/retriever.py`).

## 5. Итоговые варианты для QuantumForge

| | A. Полностью облако | B. Полностью локально | **C. Гибрид (рекомендуется)** | D. Yandex Cloud стек |
|---|---|---|---|---|
| LLM | GPT-4o mini / Claude Haiku 5.5 | Llama 3.1 70B на своих GPU | Claude Haiku 5.5 (или GPT-4o mini) для общего контура; Llama 3.1 8B на 1×L4 для конфиденциального | YandexGPT Pro 5.1 |
| Эмбеддинги | text-embedding-3-small | bge-base-en-v1.5 / bge-m3 | bge-base-en-v1.5 локально | Yandex Embeddings |
| Хранилище | ChromaDB в EKS | Qdrant / ChromaDB | ChromaDB (прототип - FAISS) с полем `confidential` в метаданных | ChromaDB |
| Стоимость/мес (оценка) | ≈ $100 (LLM $40 + VM) | ≈ $4 000-6 000 (GPU) + 0.5 FTE ML-инженера | ≈ $700-900 ($40 LLM + $500 L4-нод + CPU-поды) | ≈ $1 500 |
| Качество | Высокое | Высокое на 70B, но дорого; на 8B - среднее | Высокое там, где важно; достаточное для конфиденциальных регламентов | Среднее на английской техдокументации |
| Конфиденциальность / GDPR / SOC 2 | Весь корпус, включая Terraform state и клиентские интеграции, уходит провайдеру - нужен DPA, EU residency и исключение части документов -> тогда бот их просто не знает | Полная | Конфиденциальные документы не покидают контур, остальное - у провайдера с DPA и EU residency | Данные в РФ - несовместимо с GDPR-обязательствами компании из ЕС |
| Сложность внедрения | 1-2 недели | 2-3 месяца + постоянная поддержка GPU | 3-5 недель | 1-2 недели, но юридически непроходим |
| Масштабируемость на внешних клиентов (цель бизнеса) | Высокая, но клиентские данные - то же ограничение | Высокая, дорогая | Высокая: контур «локальная модель» можно продавать on-prem клиентам (ABB, Wärtsilä), облачный - как SaaS | Низкая за пределами РФ |

**Выбор: вариант C, гибрид.**

1. **Эмбеддинги локальные** (bge-base-en-v1.5 на CPU-нодах EKS): весь корпус индексируется внутри контура, нет зависимости от внешнего API, стоимость - ноль, качество не хуже text-embedding-3-small.
2. **Хранилище - ChromaDB** в EKS с метаданными `space`, `owner`, `updated_at`, `confidential`. В прототипе - FAISS (`build_index.py`), чтобы не усложнять учебный проект; переход на Chroma - замена одного модуля.
3. **LLM - двухконтурная.** Запросы к публичной части базы идут в Claude Haiku 5.5 / GPT-4o mini (≈ $40/мес, DPA + EU residency); если ретривер вернул чанки с `confidential=true`, запрос маршрутизируется в локальную Llama 3.1 8B на одном L4 (≈ $500/мес). Так 80% трафика получает лучшее качество за копейки, а Terraform state и клиентские интеграции не покидают контур.
4. **Сервер:** CPU-поды 8 vCPU / 32 ГБ для индексации и Chroma + один GPU-нод L4 24 ГБ для локальной модели. Всё в существующем EKS через ArgoCD, никакой новой платформы.
5. **Почему не A:** компания готовится к SOC 2 и живёт под GDPR; отправка всего корпуса, включая Terraform state и спецификации клиентов-энергокомпаний, внешнему провайдеру - риск, который GRC не согласует. **Почему не B:** $5k/мес и отдельный ML-инженер ради качества, которое для 80% вопросов облачная модель даёт за $40. **Почему не D:** юрисдикция.

Для учебного проекта из варианта C реализован «облачный контур»: локальные эмбеддинги (all-MiniLM-L6-v2) + FAISS + Claude Haiku 5.5 через LangChain, с переключением провайдера переменной `LLM_PROVIDER` (anthropic / openai / ollama), чтобы «локальный контур» на Ollama включался без изменения кода.
